Multi-factor authentication is still one of the most effective ways to reduce the impact of stolen passwords. **AuthQuake** is a useful reminder that MFA security depends on the verifier behind the second factor: how it limits attempts, correlates sessions and exposes suspicious activity.

The issue reported in 2024 concerned Microsoft's implementation of six-digit codes generated by Microsoft Authenticator. The weakness was not a failure of MFA as a concept, and it was not a generic bypass affecting every authenticator. The problem was that failed guesses could be distributed across multiple sign-in sessions instead of being constrained by one effective limit for the account.

An attacker still needed a valid username and password. In the researchers' tests, the victim did not need to approve a push notification or interact with the attack. That made the weakness especially serious for accounts protected only by a code-based Authenticator flow.

<!--more-->

## The short version

- **AuthQuake targeted:** the six-digit one-time-code flow in Microsoft Authenticator.
- **Precondition:** the attacker already had the target's username and password.
- **Core weakness:** failed attempts were limited per session instead of being effectively aggregated across concurrent sessions.
- **Observed effect:** repeated guesses could continue during the code's validity window.
- **User interaction:** none was required in the researchers' tests.
- **Detection challenge:** no useful notification was observed during those tests.
- **Microsoft response:** a temporary fix was deployed on July 4, 2024, followed by a permanent fix on October 9, 2024.

The important conclusion is precise: this was an implementation and abuse-control flaw in one MFA path, not evidence that all MFA is pointless. Strong MFA, especially phishing-resistant authentication, remains a critical control.

> **Lab safety:** this article does not include code to automate guesses, create sessions against Microsoft or test a real account. The demonstration below is a local rate-limit model with no network I/O. Test only an identity provider and accounts that you own.

## How code-based MFA is supposed to work

A time-based one-time password (TOTP) is generated from a shared secret and a time step. The verifier accepts a code only for a short validity window, usually around 30 seconds, with limited tolerance for clock drift.

For a six-digit code there are one million possible values. That number alone is not the security boundary. The practical boundary is the combination of:

1. a short validity window;
2. a strict limit on failed attempts;
3. a limit applied to the account or authentication transaction, not just to one browser session;
4. useful alerts and audit events;
5. a safe recovery process when the account is under attack.

If the verifier counts only attempts in the current session, an attacker can try to reset that counter by creating more sessions. The code space has not changed, but the number of guesses allowed before the code expires has.

## What was actually broken?

AuthQuake was built around a mismatch between the intended control and the control that was effectively enforced:

1. A valid username and password opened a Microsoft sign-in flow.
2. The flow requested a six-digit code from Microsoft Authenticator.
3. One session accepted only a bounded number of failed attempts.
4. New concurrent sessions could obtain their own attempt budget.
5. The attacker distributed guesses across those sessions while the code remained valid.
6. A correct code completed the sign-in without a user approving a push notification.

The exact thresholds and timings are implementation-specific. In the researchers' testing, a code was observed to remain usable for roughly three minutes and the cumulative success probability passed 50% after about 24 sessions, or approximately 70 minutes of repeated attempts. Those figures describe the tested behaviour; they are not universal properties of TOTP or a recommended test plan.

This distinction matters when communicating the risk. AuthQuake was not:

- a password-cracking technique;
- a session-cookie theft technique;
- a push-notification fatigue attack;
- a generic bypass of all MFA methods;
- a remote-code-execution vulnerability.

It was an abuse of a code-verification flow whose rate limiting did not sufficiently follow the account across sessions.

## The attack scenario

Consider an account that uses Microsoft Authenticator codes as its second factor:

1. Credentials for the account have already been exposed through phishing, reuse or a separate breach.
2. The attacker starts a normal remote sign-in and reaches the MFA challenge.
3. Instead of asking the user to approve a push, the attacker submits guesses to the six-digit code form.
4. The attacker opens additional sessions so that failed attempts are not governed by one effective account-level budget.
5. A correct code, if reached before the validity window closes, completes authentication.
6. The attacker receives the access already granted to that account: mailbox, files, applications or administrative functions.

The MFA factor still adds entropy and blocks ordinary password-only attempts. The problem is that the verifier makes too many guesses economically viable. The account's permissions and the attacker's already-stolen password determine the final impact.

## Why aggregate rate limiting matters

Let p be the chance that one independent code guess succeeds within a validity window and let n be the number of guesses that the verifier permits during that window. The cumulative probability can be approximated as:

~~~text
P(success) = 1 - (1 - p)^n
~~~

This is only a simplified model. Real attempts are affected by code expiry, clock skew, concurrency, network latency and server-side controls. It is nevertheless useful for explaining why “ten attempts per session” is not equivalent to “ten attempts per account”.

A robust verifier should maintain the security state in a shared store and apply limits across the dimensions that matter:

- account or principal;
- authentication transaction;
- tenant;
- source risk and network reputation;
- device and session family;
- recent failed-factor history.

IP-only limits are not enough: they can block a whole office while allowing a distributed attack to continue. Session-only limits are not enough either: they can be reset by opening more sessions.

## Safe local demonstration of aggregate rate limiting

A real reproduction would automate sign-in sessions against an identity provider. That is unnecessary and unsafe. The following local Python model compares a vulnerable per-session counter with a hardened account-level counter. It uses no HTTP requests, no MFA provider and no real codes.

Save it as **mfa-global-rate-limit-model.py** and run:

~~~bash
python mfa-global-rate-limit-model.py
~~~

The command is intentionally named **mfa-global-rate-limit-model** to make the security property being tested explicit.

~~~python
from dataclasses import dataclass, field


COMMAND_NAME = "mfa-global-rate-limit-model"


@dataclass
class AccountGuard:
    max_attempts: int = 10
    cooldown_seconds: int = 12 * 60 * 60
    attempts: dict[str, int] = field(default_factory=dict)
    locked_until: dict[str, int] = field(default_factory=dict)

    def allow(self, account: str, now: int) -> bool:
        if now < self.locked_until.get(account, 0):
            return False

        current = self.attempts.get(account, 0)
        if current >= self.max_attempts:
            self.locked_until[account] = now + self.cooldown_seconds
            return False

        self.attempts[account] = current + 1
        return True


def per_session_policy(session_attempts: int, max_attempts: int = 10) -> bool:
    """Model the unsafe property: every new session gets a new counter."""
    return session_attempts < max_attempts


print(COMMAND_NAME)

for session in ("session-1", "session-2", "session-3"):
    allowed = sum(
        per_session_policy(attempt)
        for attempt in range(10)
    )
    print(f"vulnerable policy: {session} allowed={allowed}")

guard = AccountGuard()
now = 0
allowed = 0

for _ in range(30):
    if guard.allow("alice", now):
        allowed += 1

print(f"hardened policy: account attempts={allowed} locked=yes")
print(f"hardened policy: next attempt={'allowed' if guard.allow('alice', now) else 'denied'}")
~~~

Expected output:

~~~text
mfa-global-rate-limit-model
vulnerable policy: session-1 allowed=10
vulnerable policy: session-2 allowed=10
vulnerable policy: session-3 allowed=10
hardened policy: account attempts=10 locked=yes
hardened policy: next attempt=denied
~~~

The model does not reproduce AuthQuake. It demonstrates the defensive invariant that must hold: opening a new session must not reset the account's MFA-attempt budget.

## Validation plan for an authorised lab

If you operate an identity provider or have a dedicated test tenant, validate the control without enumerating real codes:

1. Submit a small number of invalid codes and confirm that the account or authentication transaction is throttled.
2. Repeat the same negative test from a new browser session and verify that the limit is not reset.
3. Check whether the limit is shared across the provider's front ends and regions.
4. Confirm that failed MFA events are visible in the provider's sign-in and audit logs.
5. Confirm that the security team receives an alert when failures are repeated or distributed.
6. Verify that a successful sign-in after a burst of failures is flagged for investigation.
7. Confirm that factor reset, password reset and session revocation invalidate pending authentication state.

Do not turn this plan into a brute-force test. The goal is to validate state management, lockout, observability and recovery—not to find a working code.

## Detection and investigation

AuthQuake-like activity is behavioural rather than signature-based. Look for combinations such as:

- a successful password step followed by repeated MFA failures;
- many sign-in sessions for one account in a short period;
- MFA failures spread across IP addresses, user agents or regions;
- a new session immediately after an unusual burst of rejected codes;
- repeated attempts against several accounts from the same infrastructure;
- factor-registration, password-reset or consent changes after a suspicious sign-in;
- access to mail, files, administration consoles or other sensitive resources after the anomaly.

Correlate identity-provider logs with endpoint, proxy, VPN and SaaS audit logs. A single failed code is normal. The combination of valid credentials, session multiplication, failed codes and eventual success is the signal worth investigating.

For a suspected compromise:

1. revoke active sessions and refresh tokens;
2. reset the password and check for password reuse;
3. re-register or verify the user's MFA factors through a trusted process;
4. review mailbox rules, OAuth consents, registered devices and persistence mechanisms;
5. inspect data access and administrative changes;
6. preserve provider logs and timestamps before retention removes them.

## Hardening priorities

### 1. Verify the provider-side fix

This class of issue cannot be fixed in a browser or mobile application alone. Confirm the provider's current behaviour and security advisories, then validate rate limiting in an authorised test tenant.

The required property is stronger than “there is a limit”: the limit must be applied across concurrent sessions and enforced by shared server-side state. The cooldown should be long enough to make repeated guessing impractical and should not reveal enough detail to help an attacker tune the attack.

### 2. Prefer phishing-resistant authentication

Use FIDO2, passkeys or WebAuthn for sensitive accounts where the platform supports them. These methods bind authentication to the legitimate origin and do not expose a reusable six-digit code that can be guessed through a remote form.

Code-based MFA remains useful, especially during migration, but it should not be the strongest option for privileged or high-impact accounts.

### 3. Make abuse visible

Alert on:

- repeated MFA failures for one account;
- failed MFA attempts distributed across sessions or locations;
- password success followed by MFA failure bursts;
- a successful login following unusual MFA activity;
- factor changes, new devices or token issuance after the event.

Notifications should help the account owner and the security team understand what happened without disclosing internal thresholds.

### 4. Reduce the value of a compromised account

Apply least privilege, conditional access, step-up authentication for sensitive actions, short-lived administrative sessions and strong controls around recovery methods. MFA protects a login; it does not decide what that account may do afterwards.

Maintain tested emergency accounts, but protect and monitor them separately. A lockout design that can be bypassed through an unprotected recovery path only moves the weakness.

## What AuthQuake teaches

AuthQuake is a good case study in the difference between an authentication factor and an authentication system. A one-time code can be mathematically strong while the surrounding verifier allows too many attempts, too much time or too little visibility.

The practical questions for any MFA deployment are therefore:

- Is the attempt budget global across sessions?
- Does the control work across a distributed provider?
- Are failures logged and alerted?
- Can suspicious sessions and tokens be revoked quickly?
- Is there a phishing-resistant option for high-value accounts?

MFA remains worth deploying. The lesson is to assess the complete verification path—rate limiting, session state, monitoring and recovery—not only the label printed on the second factor.
