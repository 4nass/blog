## The short version

**CVE-2024-3596**, known as **Blast-RADIUS**, is a protocol-level weakness in legacy RADIUS authentication. An attacker who can observe and modify the traffic between a RADIUS client—such as a VPN gateway, switch or wireless controller—and the RADIUS server can forge an authentication response.

The attack abuses the **MD5 Response Authenticator** defined by the older RADIUS/UDP protocol. When the flow does not require a `Message-Authenticator`, a chosen-prefix collision can make a modified response appear valid to the client without revealing the shared secret.

The practical consequence can be an **Access-Reject changed into an Access-Accept**, or an `Access-Challenge` changed into an `Access-Accept` in some MFA flows. This is not a remote Internet attack against every RADIUS deployment: the attacker needs an on-path position, and the exact impact depends on the client, server, authentication method and configuration.

> **Lab safety:** the demonstration below is a local integrity model and packet-audit procedure. It does not generate a forged RADIUS packet, perform an MD5 collision or attempt authentication against a real network. Run any packet capture only on a lab network that you own.

The [CERT Coordination Center note VU#456537](https://kb.cert.org/vuls/id/456537) explains that an on-path attacker can transform one RADIUS response into another when `Message-Authenticator` is not required or enforced. The [NVD record](https://nvd.nist.gov/vuln/detail/CVE-2024-3596) lists the protocol as affected and gives the vulnerability a CVSS 3.1 score of 9.0.

## RADIUS in one minute

RADIUS is a request-response protocol used to centralize authentication and authorization for network access. A typical flow looks like this:

1. A network access device (the **NAS** or RADIUS client) sends an `Access-Request` to the RADIUS server.
2. The server evaluates the credentials and policy against a directory or identity provider.
3. The server returns `Access-Accept`, `Access-Reject` or `Access-Challenge`.
4. The NAS grants, denies or continues access based on that response.

In the classic UDP design, the response contains a `Response Authenticator` calculated with MD5 and a shared secret known to the client and server. That mechanism was intended to provide integrity, but it leaves a weakness when the attacker can alter the packet and the flow does not carry the stronger `Message-Authenticator` attribute.

## What is actually broken?

Blast-RADIUS is not a password-cracking bug and it does not require the attacker to learn the RADIUS shared secret. The weakness is in how the client validates the response it receives:

1. The attacker obtains an on-path position, for example on an untrusted network segment, compromised router path or exposed virtualization boundary.
2. A legitimate `Access-Request` travels from the NAS to the server.
3. The server sends a valid response, often an `Access-Reject` for the test credentials.
4. The attacker intercepts and modifies the exchange while it is in transit.
5. The attacker uses a chosen-prefix MD5 collision to preserve the response check while changing the response semantics.
6. The NAS accepts the forged result if the flow did not require the stronger `Message-Authenticator` validation.

The result is a protocol-level authorization decision being forged in transit. The directory password, private key and RADIUS shared secret may all remain unknown to the attacker.

## Why MD5 is relevant here

MD5 is not being used as a password hash in this attack. It is part of the legacy RADIUS response-integrity construction. Cryptographic collision attacks make it possible to construct two different inputs with the same digest under carefully controlled conditions.

RADIUS makes the attack practical because some of the response input is predictable and because the attacker can influence or relay parts of the request-response exchange. The attack is computationally expensive and time-sensitive, but it does not need to recover the shared secret.

That distinction matters operationally: simply rotating the RADIUS shared secret is not a complete fix if the protocol still accepts the vulnerable response-validation path.

## Which flows are most exposed?

The risk is highest when all of the following conditions meet:

- RADIUS authentication is carried over a transport that an attacker can observe and modify, commonly UDP;
- the client and server accept a flow without enforcing `Message-Authenticator`;
- the NAS makes an access-control decision from the forged response;
- the attacker can maintain an on-path position long enough to perform the collision work.

RADIUS deployments that only use EAP with the required `Message-Authenticator` are not vulnerable to this attack path according to the CERT/CC note. RADIUS/TLS and RADIUS/DTLS protect the transport from the relevant modification. Plain RADIUS over TCP should not automatically be considered fixed; use TLS or DTLS and verify the vendor guidance.

The scope is implementation-specific. CERT-FR lists, for example, FreeRADIUS 3.2.x versions before 3.2.5 and versions before 3.0.27 as affected, but network appliances, VPN products, operating systems and cloud services must be checked against their own advisories.

## The attack scenario

Imagine a VPN gateway using PAP over RADIUS/UDP:

1. A user enters invalid credentials, so the RADIUS server prepares an `Access-Reject`.
2. The attacker is positioned between the VPN gateway and the RADIUS server.
3. The attacker intercepts the request and response and prepares a response with the same observable structure but an `Access-Accept` outcome.
4. The gateway verifies the legacy response authenticator and accepts the forged result.
5. The gateway creates a VPN session using the authorization attributes supplied in the forged response or its local defaults.

The attacker has not authenticated to the directory. They have forged the protocol decision made by the gateway. If the flow carries an `Access-Challenge` for MFA and the deployment does not enforce the required integrity attribute, the same class of response substitution can potentially bypass the challenge.

This scenario is deliberately simplified. A real attack depends on the exact NAS, RADIUS server, authentication method, proxy path and packet layout. Do not treat it as a claim that every VPN or every RADIUS exchange is exploitable.

## Safe local demonstration of the validation boundary

A real Blast-RADIUS proof of concept would construct collision material and manipulate live RADIUS packets. That is not necessary to demonstrate the defensive requirement. The following local Python model shows the security property: a response without the required `Message-Authenticator` must not be accepted merely because its legacy response field appears consistent.

Save it as `radius-message-authenticator-gate.py` and run it with Python. It performs no network I/O:

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class RadiusResponse:
    code: str
    response_authenticator_valid: bool
    message_authenticator_valid: bool


def validate_response(response: RadiusResponse, require_message_authenticator: bool) -> str:
    if not response.response_authenticator_valid:
        return "REJECT: legacy response validation failed"

    if require_message_authenticator and not response.message_authenticator_valid:
        return "REJECT: Message-Authenticator is required"

    return f"ACCEPT: {response.code}"


legacy_flow = RadiusResponse(
    code="Access-Accept",
    response_authenticator_valid=True,
    message_authenticator_valid=False,
)

patched_flow = RadiusResponse(
    code="Access-Accept",
    response_authenticator_valid=True,
    message_authenticator_valid=True,
)

print("radius-message-authenticator-gate")
print("legacy policy :", validate_response(legacy_flow, False))
print("hardened policy:", validate_response(patched_flow, True))
print("forged-shape  :", validate_response(legacy_flow, True))
```

Expected output:

```text
radius-message-authenticator-gate
legacy policy : ACCEPT: Access-Accept
hardened policy: ACCEPT: Access-Accept
forged-shape  : REJECT: Message-Authenticator is required
```

This is a policy model, not a reproduction of the cryptographic collision. Its purpose is to make the remediation testable in code and to prevent a misleading “working exploit” claim in a portable blog post.

## Auditing a real RADIUS capture

If you own a lab RADIUS path, capture a normal authentication exchange and inspect whether the required attribute is present. The following read-only command is named `radius-message-authenticator-audit`:

```bash
tshark -r radius-lab.pcapng \
  -Y 'radius' \
  -T fields \
  -E header=y \
  -E separator='\t' \
  -e frame.number \
  -e ip.src \
  -e ip.dst \
  -e radius.code \
  -e radius.message_authenticator
```

Example interpretation:

```text
frame.number  ip.src       ip.dst        radius.code  radius.message_authenticator
42            192.0.2.10   192.0.2.20    Access-Request  7f:...
43            192.0.2.20   192.0.2.10    Access-Reject   7f:...
```

The exact Wireshark field name and display vary by version. A missing field is not by itself a complete vulnerability verdict: confirm the authentication method, proxy behaviour and vendor requirement. Do not capture production credentials or share a capture containing usernames, attributes or secrets.

## FreeRADIUS hardening example

For FreeRADIUS, upgrade first. CERT-FR identifies versions before **3.2.5** and before **3.0.27** as affected. The FreeRADIUS security guidance also recommends requiring `Message-Authenticator` for clients and handling proxy paths explicitly.

The following is an illustrative client definition for an isolated lab. The exact option location depends on the FreeRADIUS version and configuration layout:

```text
client lab-nas {
    ipaddr = 192.0.2.10
    secret = <lab-only-shared-secret>
    require_message_authenticator = yes
}
```

After changing the lab configuration:

1. Validate the configuration with the distribution’s FreeRADIUS validation command.
2. Restart the lab service.
3. Capture one successful and one rejected authentication exchange.
4. Confirm that the expected `Message-Authenticator` is present and validated.
5. Test all proxies and NAS devices before applying the setting broadly.

If a legacy NAS cannot send the required attribute, do not silently assume that the network is protected. Upgrade or replace the device, isolate the path, or move the flow to RADIUS/TLS or RADIUS/DTLS where supported.

## Detection and investigation

Look for a combination of protocol and access-control signals:

- RADIUS/UDP traversing a network segment that is not strictly controlled;
- `Access-Accept`, `Access-Reject` or `Access-Challenge` responses without the expected `Message-Authenticator`;
- a rejected credential event followed immediately by a successful VPN, Wi-Fi, switch or administrative session;
- authorization attributes that change unexpectedly between normal and anomalous sessions;
- a new or unusual network path between the NAS and the RADIUS server;
- packet captures showing inconsistent request/response timing, duplicate responses or responses from an unexpected source;
- RADIUS proxies that strip, rewrite or fail to validate the attribute.

Review the NAS logs, RADIUS server logs, VPN or wireless-controller session records and network telemetry together. A valid-looking `Access-Accept` is not sufficient evidence that the user successfully authenticated at the identity source.

## Remediation and hardening

### 1. Patch every implementation in the path

Identify every RADIUS client, proxy and server involved in authentication. Apply vendor fixes to the full chain, not just the central server. For FreeRADIUS, move to **3.2.5** or **3.0.27** and verify the package revision supplied by the distribution.

### 2. Require `Message-Authenticator`

Enforce the attribute on all applicable authentication flows, especially non-EAP flows and proxied requests. Verify that the NAS, proxy and server all support the requirement; one legacy device behind a proxy can leave the path exposed.

For EAP, confirm that the implementation follows the requirement from RFC 3579. EAP-only does not mean “safe by label”; the attribute must actually be present and validated.

### 3. Encrypt or isolate the transport

Prefer RADIUS/TLS (RadSec) or RADIUS/DTLS where the product ecosystem supports it. If the organization must continue using RADIUS/UDP during migration:

- place the traffic on a dedicated management network;
- restrict the path with firewall rules and authenticated tunnels;
- prevent untrusted hosts from injecting or modifying UDP packets;
- remove direct Internet exposure;
- monitor unexpected changes in the NAS-to-server route.

Network isolation is a compensating control. It does not remove the protocol weakness if an attacker can still obtain an on-path position.

### 4. Test authorization, not only authentication

After patching, test rejected credentials, MFA challenges, proxy flows and authorization attributes. Confirm that a client cannot obtain network access after the identity provider rejects the request and that legitimate EAP and non-EAP flows continue to work.

## Takeaways

Blast-RADIUS is a failure of message integrity at the point where a network device turns a RADIUS response into an access decision. The critical questions are not only “which RADIUS server do we run?” but also:

- can an attacker reach the network path?
- is `Message-Authenticator` mandatory and validated?
- are proxies and NAS devices patched and compatible?
- can the transport be moved to TLS or DTLS?

Patch the entire RADIUS chain, enforce the stronger attribute, isolate legacy UDP traffic and validate the result with captures and access-control tests. Rotating shared secrets or enabling MFA alone does not address a response-forgery path that occurs before the client accepts the authentication decision.
