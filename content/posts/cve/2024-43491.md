## The short version

**CVE-2024-43491** is a critical vulnerability in the Windows **Servicing Stack**, the part of Windows responsible for evaluating and applying updates. On a narrow but important target—**Windows 10 version 1507** with certain optional components—the defect could roll back fixes that had already been delivered.

The result is not a magic “Windows Update command” that immediately opens a shell. The update defect changes the security state of the machine: a previously fixed vulnerability in an optional component can become vulnerable again. An attacker can then use that reintroduced weakness as the final step of the attack chain.

> **Lab safety:** the checks in this article are read-only. Run them only on a disposable Windows 10 version 1507 virtual machine that you own. Do not remove updates, enable optional components or send exploit traffic to a production system.

## At a glance

| Field | Details |
| --- | --- |
| Affected component | Windows Servicing Stack / Windows Update |
| Affected platform | Windows 10 version 1507, principally Enterprise 2015 LTSB and IoT Enterprise 2015 LTSB |
| Attack precondition | A vulnerable build with an affected optional component and a reintroduced component flaw |
| Impact | Remote code execution through a vulnerability that had previously been mitigated |
| Severity | Critical — CVSS 3.1: 9.8 |
| Vulnerable update window | KB5035858 or later updates through August 2024 on the affected release |
| Remediation | Install SSU KB5043936, then security update KB5043083; preferably migrate from Windows 10 version 1507 |

Microsoft describes the issue as a Servicing Stack vulnerability that rolled back fixes for some vulnerabilities affecting Optional Components. The CVE record assigns a **9.8** CVSS score and records the two September 2024 updates required to address it. See the [Microsoft Security Update Guide](https://msrc.microsoft.com/update-guide/vulnerability/CVE-2024-43491) and the [NVD record](https://nvd.nist.gov/vuln/detail/CVE-2024-43491).

## What is actually broken?

Windows updates are not just copied onto disk. The servicing stack decides whether a package applies to a particular operating-system build and optional component. That decision is a security boundary: a component that received a security fix must not silently return to an older, vulnerable state.

The vulnerable sequence can be represented like this:

1. An optional Windows component is installed on a Windows 10 version 1507 system.
2. A security update patches a vulnerability in that component.
3. A later servicing evaluation incorrectly treats the component update as not applicable.
4. The component files are rolled back to an older baseline.
5. The security fix is no longer present, even though the machine may appear to have received recent updates.
6. An attacker reaches the optional component and exploits the reintroduced vulnerability.

The important distinction is between the **rollback defect** and the **final component exploit**. CVE-2024-43491 creates the unsafe state; the exact network request, payload and resulting process depend on the optional component and the vulnerability that was exposed again. A generic proof of concept for “Windows Update” would therefore be misleading.

## Who was exposed?

The affected scope is much narrower than “all Windows 10 systems”:

- Windows 10 version 1507, the initial Windows 10 release from July 2015;
- Enterprise 2015 LTSB and IoT Enterprise 2015 LTSB editions that remained in support;
- systems with the March 2024 security update **KB5035858**, or subsequent updates released through August 2024;
- systems with one or more of the optional components covered by the servicing defect.

Later versions of Windows 10 were not impacted by this CVE. Windows 10 version 1507 is also long out of general support, which makes migration the safer long-term answer than trying to preserve an old servicing baseline.

## The attack chain

### Stage 1 — Find a legacy target

An attacker first identifies a machine that still exposes Windows 10 version 1507. Useful signals include asset inventory, service banners, management data or an externally reachable service provided by an optional component.

The CVSS vector is network-based and requires no privileges or user interaction, but that does not mean that every vulnerable machine is reachable from the Internet. Exposure still depends on the component enabled by the deployment and the network path to it.

### Stage 2 — Confirm the servicing state

The attacker looks for the combination that matters: an affected Windows build, an optional component, and a servicing state in which its security fix may have been rolled back. This is why the installed KB list alone is not sufficient evidence; the component inventory and package state must also be checked.

### Stage 3 — Exploit the reintroduced component flaw

The final request targets the optional component, not Windows Update itself. If the component is listening and its older vulnerable files are present, a previously mitigated vulnerability may once again provide remote code execution.

This article intentionally does not include a weaponised payload or a component-specific exploit. The safe and reproducible part is the state assessment below; the offensive chain would require a real, vulnerable Windows VM and a separate exploit for the affected component.

## A safe exposure check

The following PowerShell check is read-only. Save it as `windows-servicing-exposure-check.ps1` if you want a repeatable evidence artifact, then run it in an elevated PowerShell window inside the lab:

```powershell
$ErrorActionPreference = "Stop"

$os = Get-CimInstance Win32_OperatingSystem
$hotfixes = Get-HotFix | Group-Object HotFixID -AsHashTable -AsString
$packages = @()

try {
    $packages = Get-WindowsPackage -Online |
        Where-Object PackageName -match 'KB5035858|KB5043936|KB5043083'
} catch {
    Write-Warning "The DISM package inventory was not available: $($_.Exception.Message)"
}

$is1507 = $os.BuildNumber -eq "10240"
$relevantKbs = foreach ($kb in 'KB5035858', 'KB5043936', 'KB5043083') {
    [pscustomobject]@{
        Update = $kb
        HotFixPresent = $hotfixes.ContainsKey($kb)
        PackagePresent = [bool]($packages.PackageName -match $kb)
    }
}

[pscustomobject]@{
    Caption = $os.Caption
    Build = $os.BuildNumber
    Architecture = $os.OSArchitecture
    IsWindows10Version1507 = $is1507
    RelevantUpdates = ($relevantKbs | Out-String).Trim()
}
```

Example output from a deliberately incomplete lab snapshot:

```text
Caption                    : Microsoft Windows 10 Enterprise 2015 LTSB
Build                      : 10240
Architecture               : 64-bit
IsWindows10Version1507     : True
RelevantUpdates            :
                             Update   HotFixPresent PackagePresent
                             ------   ------------- --------------
                             KB5035858          True           True
                             KB5043936         False          False
                             KB5043083         False          False
```

This output is a triage signal, not proof that a particular optional component is exploitable. It tells the defender that the system is in the relevant legacy family and that the September remediation pair is absent. The next step is to inventory optional components and compare their package/file state with the vendor guidance.

## A deterministic local model of the flaw

Because the vulnerable logic lives inside the proprietary Windows servicing stack, a portable lab cannot faithfully reproduce it without a licensed, disposable Windows 10 version 1507 image. The following model demonstrates the security property being tested: a component marked as patched must not be returned to its vulnerable baseline by an update evaluation.

The command is intentionally named `servicing-stack-rollback-proof` to make clear that it proves the unsafe state transition; it does not alter Windows or execute a payload:

```powershell
function Invoke-ServicingStackRollbackProof {
    param(
        [Parameter(Mandatory)] [bool] $OptionalComponentPresent,
        [Parameter(Mandatory)] [bool] $ComponentWasPatched,
        [Parameter(Mandatory)] [bool] $ServicingStackRolledBackFix,
        [Parameter(Mandatory)] [bool] $SeptemberRemediationApplied
    )

    $state = if (-not $OptionalComponentPresent) {
        'NOT_APPLICABLE'
    } elseif ($SeptemberRemediationApplied) {
        'FIXED'
    } elseif ($ComponentWasPatched -and $ServicingStackRolledBackFix) {
        'PATCH_ROLLED_BACK'
    } elseif ($ComponentWasPatched) {
        'PATCH_PRESENT'
    } else {
        'COMPONENT_UNPATCHED'
    }

    [pscustomobject]@{
        Command = 'servicing-stack-rollback-proof'
        State = $state
        SecurityMeaning = switch ($state) {
            'PATCH_ROLLED_BACK' { 'A previously applied fix is absent; remediation is required.' }
            'COMPONENT_UNPATCHED' { 'The component has no recorded fix; do not expose it.' }
            'FIXED' { 'The September remediation pair is recorded as applied.' }
            'PATCH_PRESENT' { 'The component fix remains present in this model.' }
            default { 'The component is not part of this scenario.' }
        }
    }
}

Invoke-ServicingStackRollbackProof `
    -OptionalComponentPresent $true `
    -ComponentWasPatched $true `
    -ServicingStackRolledBackFix $true `
    -SeptemberRemediationApplied $false
```

Expected result:

```text
Command                         State               SecurityMeaning
-------                         -----               ---------------
servicing-stack-rollback-proof PATCH_ROLLED_BACK    A previously applied fix is absent; remediation is required.
```

The model does not claim to exploit Windows. It gives a clean regression test for detection logic and makes the core failure visible without downgrading a real operating system or sending attack traffic.

## Validating a real lab machine safely

If you have an authorised Windows 10 version 1507 image, keep the validation focused on evidence:

1. Take a snapshot before installing or inspecting any test component.
2. Disconnect the VM from the public Internet; use an isolated host-only network if network reachability is required.
3. Record the edition, build number, installed optional components, installed KBs and package versions.
4. Run the read-only check above and export the output to the lab case folder.
5. Validate that the September Servicing Stack Update is installed **before** the September security update.
6. Confirm that the vulnerable component is no longer serving an old binary or exposing an unexpected network listener.
7. Revert or destroy the VM when the test is complete.

Do not uninstall KB5043936 or KB5043083 to manufacture a vulnerable state on a workstation, and do not use an Internet-facing machine as the test target. The published remediation is the correct way to validate patch management: install the SSU first, then the security update.

## Detection and investigation

Look for evidence of both halves of the attack chain:

- Windows 10 version 1507 hosts with optional components enabled and a missing September 2024 SSU or security update;
- component files whose version or package ownership is older than the expected patched baseline;
- servicing and CBS logs showing package applicability, rollback or unexpected component state changes;
- network requests to optional-component services from sources that do not normally use them;
- a suspicious child process, service creation, account change or outbound connection immediately after activity against an optional component;
- asset records that report a recent cumulative update while the component inventory still contains an older binary.

The strongest signal is not one event ID. It is the correlation between **legacy platform**, **optional component**, **unexpected package state** and **post-exploitation behaviour**.

## Remediation and hardening

### 1. Apply the remediation pair in order

For the affected release, Microsoft’s remediation requires both updates:

1. Install the September 2024 Servicing Stack Update **KB5043936**.
2. Install the September 2024 Windows security update **KB5043083**.
3. Restart when required and verify the resulting build and package state.

The [KB5043936 servicing stack bulletin](https://support.microsoft.com/en-US/servicing/os/windows/ssu/2024/09/kb5043936-servicing-stack-update-for-windows-10-september-10-2024) documents the SSU. The [KB5043083 security update](https://support.microsoft.com/help/5043083) is the companion September update for Windows 10 version 1507.

### 2. Prefer migration over indefinite containment

Windows 10 version 1507 is a legacy platform. Where the workload permits it, migrate to a supported Windows release or replace the legacy workload. A compensating control around an old optional component should be treated as temporary risk reduction, not as a substitute for lifecycle management.

### 3. Reduce the reachable attack surface

- Remove optional components that are not required.
- Disable or restrict network access to components that must remain installed.
- Keep legacy hosts off the public Internet and behind tightly scoped administrative paths.
- Segment legacy workloads from identity, management and backup infrastructure.
- Alert when a component is enabled or when a legacy host receives an unexpected package change.

## Takeaways

CVE-2024-43491 is a useful reminder that patch state is not just a list of KB numbers. An update mechanism can become part of the attack surface when its applicability logic is allowed to return a component to an older security state.

The practical response is straightforward: identify the narrow Windows 10 version 1507 scope, verify optional-component package state, apply **KB5043936 before KB5043083**, and plan the retirement of the legacy platform. Treat any post-rollback component activity as a potential intrusion chain rather than as an ordinary update failure.
