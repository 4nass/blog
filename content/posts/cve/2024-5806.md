## The short version

**CVE-2024-5806** is an improper-authentication vulnerability in the SFTP module of Progress MOVEit Transfer. In a vulnerable configuration, an attacker can make the server treat an invalid public-key authentication attempt as if the key stage had succeeded, then continue the authentication flow as another user.

The practical impact is account impersonation: once authenticated, the attacker can access the files and permissions available to the selected SFTP account. The vulnerability is not a generic remote-code-execution flaw, and it does not mean that every MOVEit installation is automatically exploitable. The SFTP service must be exposed and the attacker must satisfy the conditions described below.

> **Lab safety:** use only an isolated MOVEit test instance that you own or are explicitly authorised to assess. Do not run a public PoC against an Internet-facing system. Keep the instance off the public Internet, deny unnecessary outbound traffic and use a disposable test account with a single non-sensitive file.

Progress published the security bulletin on June 25, 2024. CERT-EU reported both a public proof of concept and active exploitation shortly after disclosure. The [CERT-EU advisory](https://cert.europa.eu/publications/security-advisories/2024-063/) also documents the affected version ranges and the two observed attack paths.

## What is actually broken?

The vulnerable flow involves several components:

1. The attacker starts an SFTP authentication request for a known or guessed username.
2. Instead of sending the expected public-key material, the request causes the server-side SSH library to load a file path.
3. The library passes an empty public-key fingerprint to MOVEit's authentication layer.
4. The authentication method rejects the empty key, but the caller incorrectly interprets the result as a partial success.
5. The session records that public-key authentication has already succeeded.
6. A subsequent authentication attempt reuses the cached state and is accepted.

The important bug is the inconsistent state transition: one layer reports that authentication failed, while the caller records the key stage as successful. The research analysis describes the relevant state as `PartialSuccess`, followed by a final `Authenticated` result on the next request.

The basic product-level prerequisites are:

- an affected MOVEit Transfer version;
- an SFTP service reachable by the tester;
- a valid SFTP username, or the ability to discover one through normal application behaviour;
- an authentication request that passes the SSH signature checks;
- for the simplest path, a way to place a key file on the server or otherwise reference a predictable server-side file.

## The two attack paths

### Path 1: authentication bypass through a server-side key path

The SFTP client normally sends a public key as part of the authentication request. The vulnerable implementation can instead be made to treat the supplied value as a path to a key file on the MOVEit server.

When the file is loaded, the underlying component can return an empty key value to MOVEit. The first authentication attempt is rejected internally, but the session state is updated as though public-key authentication had been completed. A second request can then pass the cached check and authenticate as the selected SFTP user.

The full attack requires more than a malformed string. The request still needs a valid username and a correctly signed SSH authentication packet. This is why the vulnerability is serious but not equivalent to an unauthenticated login against every MOVEit server.

### Path 2: forced authentication and credential exposure

The same file-loading behaviour can be abused with a network path. If the MOVEit server is allowed to make outbound SMB connections, it may attempt to authenticate to a server controlled by the tester. That can expose a Net-NTLMv2 challenge-response for the MOVEit service account.

This is a separate impact path from the direct authentication bypass. It depends heavily on Windows configuration, account privileges and network egress controls. This article does not include a credential-capture setup: the relevant defensive lesson is to block unnecessary outbound SMB/NTLM traffic and ensure that the MOVEit service account cannot be used for remote logon.

## A safe local demonstration of the state flaw

MOVEit Transfer is proprietary software and there is no official public Docker image or source tree that can be used to claim a faithful product reproduction. The following small Python program models the authentication state transition described above. It is a local regression demonstration, not MOVEit code and not a network exploit.

Save it as `moveit-auth-state-demo.py`:

```python
from dataclasses import dataclass


@dataclass
class Session:
    key_already_authenticated: bool = False


def vulnerable_authenticate(session: Session, public_key_fingerprint: str) -> str:
    if not public_key_fingerprint and not session.key_already_authenticated:
        # The vulnerable caller records partial success after rejection.
        session.key_already_authenticated = True
        return "PARTIAL_SUCCESS"

    if session.key_already_authenticated:
        return "AUTHENTICATED"

    return "DENIED"


def fixed_authenticate(session: Session, public_key_fingerprint: str) -> str:
    if not public_key_fingerprint:
        return "DENIED"

    return "AUTHENTICATED"


vulnerable_session = Session()
print(vulnerable_authenticate(vulnerable_session, ""))
print(vulnerable_authenticate(vulnerable_session, ""))

fixed_session = Session()
print(fixed_authenticate(fixed_session, ""))
```

Run it locally:

```bash
python moveit-auth-state-demo.py
```

Expected output:

```text
PARTIAL_SUCCESS
AUTHENTICATED
DENIED
```

The first two lines represent the vulnerable state transition. The final line represents the corrected behaviour: an empty key remains a failed authentication and cannot prime the session for a later success.

## Validating the real product safely

The model above is useful for explaining the bug, but it does not prove that a particular MOVEit installation is vulnerable. Product-level validation requires an authorised MOVEit Transfer instance and a controlled test account.

### 1. Isolate the test instance

- Place the server on a private lab network.
- Restrict inbound access to the tester's IP address.
- Block outbound SMB, WebDAV and unnecessary Internet traffic.
- Take a snapshot before testing.
- Use a test account such as `cve-5806-lab-user` with one file named `cve-5806-sentinel.txt`.
- Do not use production credentials, customer data or a domain administrator account.

### 2. Record the baseline

Before testing, record the MOVEit Transfer version and confirm that a normal SFTP login using the test account behaves as expected. A legitimate key should list only the sentinel file:

```text
cve-5806-sentinel.txt
```

Also record the normal failed-login event and the SFTP service logs. This makes it possible to distinguish the vulnerability test from an ordinary authentication failure.

### 3. Use the published PoC only inside the lab

The researchers who analysed the vulnerability published a Python PoC in the [`watchTowr-vs-progress-moveit_CVE-2024-5806` repository](https://github.com/watchtowrlabs/watchTowr-vs-progress-moveit_CVE-2024-5806). Review the code, pin the copy used for the test and run it only against the isolated lab address.

The PoC expects a target address, a test username and test key material. Keep the target as a private lab address and use a dedicated key pair. Do not expose the PoC command or the MOVEit SFTP port to the public Internet while testing.

After reviewing the code and installing the dependencies listed by the repository, run it only against the isolated lab instance:

```bash
python watchTowr-vs-progress-moveit_cve-2024-5806.py \
  --target-ip <MOVEIT_LAB_IP> \
  --target-user cve-5806-lab-user \
  --ppk lab_key.ppk \
  --pem lab_key
```

The target address, username and key files above are placeholders for the lab. Never replace them with a production or Internet-facing target. The script's `--help` output and repository documentation are the source of truth for the exact options used by the checked-out version.

On an affected build, the evidence to capture is:

- the SFTP authentication request and server response;
- log entries showing contradictory key-validation states;
- successful access to `cve-5806-sentinel.txt` as the test account;
- the absence of access to any other account's files.

The successful result should be limited to the test account and its sentinel file:

```text
(+) Authentication succeeded.
(+) Listing files in home directory of user cve-5806-lab-user:

cve-5806-sentinel.txt
```

On a fixed build, the same attempt should remain denied and the sentinel file should not be accessible through the bypass path. Delete the lab account and destroy the instance after testing.

## Detection and investigation

Review the following signals around the disclosure and patch window:

- successful SFTP logins without the expected public-key fingerprint;
- repeated authentication attempts for valid usernames;
- log messages that combine failed key validation with a later “client key validation successful” or partial-authentication state;
- unusual requests to MOVEit guest-access endpoints, especially when they contain key-like or path-like data;
- outbound SMB or WebDAV connections from the MOVEit server;
- access to files outside the normal activity profile of the account;
- unexpected changes to SSH key material or MOVEit logs.

The investigation should include SFTP logs, web logs, Windows security events, firewall flows and file-access auditing. If the service account may have authenticated to a remote SMB endpoint, rotate its credentials and investigate the account's remote-logon exposure.

## Mitigation and hardening

### 1. Apply the vendor fix

Upgrade MOVEit Transfer to at least one of the fixed versions:

- 2023.0.11
- 2023.1.6
- 2024.0.2

Use the current supported release recommended by Progress rather than stopping at an old fixed version.

### 2. Restrict network reachability

- Keep SFTP inaccessible from the public Internet when it is not required.
- Block outbound SMB and WebDAV from the MOVEit server.
- Prevent the MOVEit service account from logging on interactively or remotely.
- Limit the service account's privileges and network reach.
- Restrict inbound RDP, as recommended by the security advisories.

### 3. Review credentials and access

If the vulnerable service was exposed or the PoC was run against it:

- rotate the MOVEit service account credentials;
- review SFTP users and recent logins;
- inspect file downloads, uploads and deletions;
- check for unexpected SSH key material;
- review Net-NTLMv2 exposure and remote authentication events;
- preserve logs before rebuilding or restoring the instance.

## Takeaways

CVE-2024-5806 is a good example of why authentication bugs need more than a severity score. The interesting part is the state machine: a rejected key can incorrectly prime a session for a later successful authentication.

The vulnerability is exploitable in real deployments, but the complete chain is conditional and product-specific. A credible technical article should therefore separate the local state-machine demonstration from the authorised MOVEit validation, explain the prerequisites, show the expected evidence and avoid presenting a mock server as a real product reproduction.
