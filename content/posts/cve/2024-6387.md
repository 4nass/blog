## The short version

**CVE-2024-6387**, known as **regreSSHion**, is a race condition in the OpenSSH server process `sshd`. When a client remains unauthenticated until `LoginGraceTime` expires, `sshd` invokes a `SIGALRM` handler asynchronously. In vulnerable builds, that handler can reach functions that are not safe to call from a signal handler.

Under the right conditions, an unauthenticated remote attacker may corrupt process state and obtain arbitrary code execution with root privileges. The attack is technically difficult and highly dependent on the operating system, libc, architecture, memory layout and distribution patches. That difficulty does not make an Internet-facing vulnerable SSH service acceptable: exploitation was demonstrated in a lab, and the pre-authentication attack surface is exposed before credentials are checked.

> **Lab safety:** the commands below are for inventory and observation only. Run the local timing demonstration only against `127.0.0.1` in a disposable VM that you own. This article deliberately does not include a race-winning exploit, heap manipulation, shellcode or instructions for targeting a remote host.

## At a glance

| Field | Details |
| --- | --- |
| Affected component | OpenSSH server (`sshd`) |
| Vulnerability class | Signal-handler race condition — CWE-364 |
| Attack precondition | Network access to `sshd`; no authentication required |
| Impact | Potential unauthenticated remote code execution as root |
| Severity | High — CVSS 3.1: 8.1; OpenSSH describes the server flaw as critical |
| Main affected range | Portable OpenSSH 8.5p1 through 9.7p1 |
| Historical range | OpenSSH before 4.4p1 may also be vulnerable without the older backports |
| Fixed upstream release | OpenSSH 9.8 / 9.8p1 |

The [OpenSSH 9.8 release notes](https://www.openssh.org/txt/release-9.8) state that Portable OpenSSH versions from 8.5p1 through 9.7p1 are affected and that the issue was fixed in 9.8. The [NVD record](https://nvd.nist.gov/vuln/detail/CVE-2024-6387) assigns a CVSS 3.1 base score of 8.1 with high attack complexity, no privileges and no user interaction.

## What is actually broken?

SSH authentication is not one blocking function. The server accepts a connection, negotiates the protocol, parses client messages and starts authentication. A timer protects this pre-authentication phase: if the client does not authenticate before `LoginGraceTime`, `sshd` sends `SIGALRM` to terminate the session.

The vulnerable path is the interaction between that timer and the normal request-processing code:

1. A client connects to the SSH service and begins the protocol exchange.
2. The client deliberately stays unauthenticated until the grace timer is close to expiring.
3. `SIGALRM` interrupts `sshd` asynchronously while it is using internal state.
4. The signal handler calls logging or memory-management code that is not async-signal-safe.
5. The interrupted operation and the handler can observe inconsistent allocator or application state.
6. Repeating carefully timed connections may turn that race into a denial of service or, on susceptible systems, code execution in the privileged server process.

The underlying issue is not a weak password, a stolen key or a failed MFA policy. It occurs before successful authentication. SSH keys and MFA remain valuable controls, but they do not replace patching `sshd`.

## Why the bug is called regreSSHion

This is a regression of **CVE-2006-5051**, an older signal-handler race condition. The unsafe behaviour had been constrained by an earlier fix, then reappeared in Portable OpenSSH 8.5p1 after changes to the logging infrastructure.

The version history is therefore easy to misread:

- versions before 4.4p1 can be vulnerable unless they contain the relevant backports for CVE-2006-5051 and CVE-2008-4109;
- 4.4p1 through 8.4p1 are not vulnerable to this particular race because the previous fix is present;
- 8.5p1 through 9.7p1 reintroduce the condition in Portable OpenSSH;
- 9.8p1 contains the upstream fix.

Distribution packages may backport the fix without changing the upstream version string. A raw comparison such as “8.7p1 equals vulnerable” is not sufficient for Debian, Ubuntu, Red Hat, SUSE or other vendors. Always check the security advisory and package revision for the distribution you operate.

## Which systems are most exposed?

The vulnerability concerns the **server**, not merely an installed SSH client. Risk is highest when all of the following are true:

- `sshd` is reachable from an untrusted network;
- the package is in the affected range and has not received the vendor backport;
- the service uses the relevant signal and libc behaviour;
- the host is a glibc-based Linux system or another platform with comparable signal-handler behaviour.

OpenBSD is not vulnerable according to the OpenSSH release notes. Other operating systems and libc implementations require a vendor-specific assessment rather than an assumption based only on the OpenSSH banner.

## The attack scenario

### 1. Pre-authentication access

The attacker needs network access to the SSH listener, commonly TCP/22. No valid username, password, private key or shell account is required to begin the pre-authentication exchange.

### 2. Repeated incomplete sessions

The attacker opens many sessions and intentionally avoids completing authentication. Each connection is timed around the server’s `LoginGraceTime`. The goal is to make `SIGALRM` interrupt a useful code path while the privileged `sshd` process is handling the connection.

### 3. Race-dependent process corruption

The attacker does not send one special “RCE packet”. They attempt to win a timing race repeatedly. On a favourable target, an interrupted allocator or logging operation may leave process state inconsistent; the signal handler then processes that state in a privileged context.

### 4. Possible root-level execution

If the race is won and the relevant memory protections are bypassed, the final consequence can be code execution as root. Qualys demonstrated the technique on 32-bit glibc systems and estimated several hours of continuous connections for a modern lab target. OpenSSH notes that 64-bit exploitation was not demonstrated at the time of the 9.8 release and that exploitability varies significantly by platform.

These timings are research conditions, not a safe threshold. A difficult exploit can still be operationally relevant when the service is public, long-lived and repeatedly reachable.

## Safe exposure assessment

The following command is named `openssh-regresshion-exposure-check`. It reads the server version, package metadata, libc information and effective pre-authentication settings. It does not connect to another host and does not change configuration:

```bash
#!/usr/bin/env bash
set -u

echo "== openssh-regresshion-exposure-check =="
printf 'Host: '; hostname
printf 'Kernel: '; uname -srmo

if command -v sshd >/dev/null 2>&1; then
    printf 'sshd binary: '
    sshd -V 2>&1 | head -n 1 || true
else
    echo 'sshd binary: not found'
fi

if command -v getconf >/dev/null 2>&1; then
    printf 'libc: '
    getconf GNU_LIBC_VERSION 2>/dev/null || echo 'not glibc or unavailable'
fi

if command -v dpkg-query >/dev/null 2>&1; then
    dpkg-query -W -f='package=${Package} version=${Version} status=${Status}\n' \
        openssh-server openssh-client 2>/dev/null || true
elif command -v rpm >/dev/null 2>&1; then
    rpm -q --qf='package=%{NAME} version=%{VERSION}-%{RELEASE}\n' \
        openssh-server openssh-clients 2>/dev/null || true
fi

if command -v sshd >/dev/null 2>&1; then
    echo 'Effective pre-authentication settings:'
    sshd -T 2>/dev/null | grep -E '^(port|listenaddress|logingracetime|maxstartups) ' || true
fi
```

Example output from an illustrative lab host:

```text
== openssh-regresshion-exposure-check ==
Host: ssh-lab
Kernel: Linux 6.1.0 x86_64 GNU/Linux
sshd binary: OpenSSH_9.2p1 Debian-2+deb12u2
libc: glibc 2.36
package=openssh-server version=1:9.2p1-2+deb12u2 status=install ok installed
Effective pre-authentication settings:
port 22
listenaddress 0.0.0.0:22
logingracetime 120
maxstartups 10:30:100
```

The output is an assessment input, not a final verdict. A downstream package can contain a backported fix while still reporting an upstream version such as `9.2p1`. If the package advisory is unclear, treat the server as requiring remediation until the vendor status is confirmed.

## A safe local demonstration of the trigger

This demonstration shows only the condition that causes the grace timer to expire. It does not attempt to win the race or exploit `sshd`.

Start a disposable local `sshd` on loopback with a short grace period. Use the configuration mechanism appropriate for the distribution; the following example keeps the service on `127.0.0.1:22222`:

```bash
sudo /usr/sbin/sshd -D -e -p 22222 \
  -o ListenAddress=127.0.0.1 \
  -o LoginGraceTime=5 \
  -o PasswordAuthentication=no \
  -o KbdInteractiveAuthentication=no
```

From a second terminal, run the deliberately named observer `regresshion-grace-period-observer`:

```bash
python3 - <<'PY'
import socket
import time

COMMAND_NAME = "regresshion-grace-period-observer"
print(f"{COMMAND_NAME}: opening a loopback pre-auth session")

with socket.create_connection(("127.0.0.1", 22222), timeout=3) as sock:
    banner = sock.recv(256).decode("ascii", errors="replace").strip()
    print(f"server banner: {banner}")
    print("waiting beyond LoginGraceTime; no authentication is attempted")
    time.sleep(7)

print("observer complete: inspect the sshd log for a pre-authentication timeout")
PY
```

Expected server-side evidence resembles:

```text
Timeout before authentication for 127.0.0.1 port 54321
```

The exact log wording varies by OpenSSH version and distribution. A timeout proves only that the timer is active. It is not proof that the host is exploitable, and a successful timeout on a patched server is expected behaviour.

## Regression-oriented validation after patching

After installing the vendor fix, validate the operational result rather than trying to reproduce the exploit:

1. Record the package version and vendor advisory reference.
2. Restart the `sshd` service using the distribution’s service manager.
3. Confirm that the new process loaded the patched package.
4. Repeat the loopback timeout observer and verify that the service remains available and does not crash.
5. Review recent `sshd`, system journal and kernel logs for unexpected restarts or core dumps.

For example, on a system using systemd:

```bash
systemctl show -p ExecMainStartTimestamp,ExecMainPID ssh.service
journalctl -u ssh.service --since "2 hours ago" --no-pager
```

Some distributions use `sshd.service` instead of `ssh.service`. The service name and package revision must be adapted to the host; the commands above are read-only.

## Detection and investigation

There is no single log line that proves a successful regreSSHion exploit. Correlate several signals:

- bursts of connections that never complete authentication;
- repeated `Timeout before authentication` messages from the same source or network range;
- unusual SSH activity followed by an `sshd` crash, restart or core dump;
- a new root process, service, scheduled task, SSH key or account appearing after abnormal pre-authentication activity;
- unexpected changes under `/etc/ssh`, `/root/.ssh` or privileged application directories;
- a vulnerable package on an Internet-facing address, especially where direct SSH exposure is not required for business operations.

Preserve the journal, package database, process accounting and network telemetry before restarting or rebuilding a suspicious host. A clean service restart after patching does not prove that the host was never compromised.

## Mitigation and hardening

### 1. Install the vendor fix

Upgrade to OpenSSH 9.8p1 or to the fixed package supplied by the operating-system vendor. The upstream release notes identify 9.8 as the release containing the race-condition fix.

Do not rely only on the displayed upstream version. Debian, Ubuntu, Red Hat, SUSE and other distributions commonly backport security fixes into their supported package branches. Check the exact package revision and advisory for each platform.

### 2. Restrict SSH exposure while patching

As temporary risk reduction:

- restrict TCP/22 to a VPN or dedicated management network;
- remove direct Internet exposure where it is not required;
- use a firewall or security group to allow only approved administration sources;
- reduce `LoginGraceTime` and review `MaxStartups` to limit unauthenticated resource consumption.

These settings reduce exposure and may make repeated attempts more expensive, but they do not fix the signal-handler race. Do not present them as a substitute for the vendor patch.

### 3. Keep post-authentication controls in place

Continue using public-key authentication, MFA where supported, least-privilege accounts, `PermitRootLogin no` and centralized logging. These controls improve the general SSH posture, but the CVE must be handled at the server package and exposure layers because its vulnerable path is pre-authentication.

## Takeaways

regreSSHion is a good example of why “SSH requires a key” is not a complete vulnerability assessment. The affected code executes before authentication is complete, and the attack depends on a race in privileged signal handling rather than on guessing credentials.

The correct response is to identify the **server** package, confirm the distribution’s backport status, patch and restart `sshd`, then reduce Internet exposure while remediation is in progress. The local demonstration above is intentionally modest: it proves the timer path and provides safe evidence without turning the article into a remotely usable exploit guide.
